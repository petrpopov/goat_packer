# Публичный Goat Packer: очередь, воркеры, хранение и Ubuntu/Docker

**Дата:** 2026-09-26. **Статус:** проект спецификации для согласования, не реализованная система.
**Область:** развитие существующего Rust + Kotlin/Spring + React приложения.
**Результат этой работы:** анализ и решения; код приложения, Docker и миграции пока не меняются.

## 1. Резюме решения

1. PostgreSQL нужен: задачи, владельцы, попытки выполнения, очередь, квоты, сроки хранения,
   ссылки на объекты и события должны переживать перезапуск. Используем Flyway и Spring Data JPA.
2. Для первого сервера **4 vCPU / 4 GiB RAM** рекомендован режим `compact`: надёжная очередь
   в PostgreSQL, один ограниченный native runner, приватное S3-хранилище. RabbitMQ не обязателен
   для надёжности такой очереди и по умолчанию здесь отключён.
3. Режим `standard`: те же данные и API, плюс RabbitMQ как транспорт команд и несколько
   исполнителей. Ориентир — от 8 GiB для испытаний, 16 GiB комфортнее для параллельного слайсинга;
   это не гарантия достаточности для любой модели. Число одновременно работающих задач —
   результат ресурсного расчёта и испытаний, а не количество HTTP-пользователей.
4. S3 — контракт хранения, а не облачная зависимость. Основной кандидат для self-hosting —
   **SeaweedFS single-node**. Legacy community MinIO не предлагается новым production-дефолтом:
   официальный репозиторий архивирован 25 апреля 2026 и объявлен неподдерживаемым [S1].
5. Браузер работает без регистрации через гостевую сессию. Необязательный аккаунт даёт
   историю и бессрочные исходники/результаты **в пределах квоты**, не безлимитный диск.
6. Гостевые результаты доступны 24 часа после завершения. Возврат — по URL с UUID и
   отдельным секретом доступа; UUID сам по себе не является авторизацией.
7. Слайсеры устанавливаются в закреплённые Linux-образы. Каждая попытка обрабатывается
   в отдельном ограниченном контейнере без сети и секретов БД/S3. Локальный scratch-диск
   остаётся необходимым, но больше не является единственным хранилищем файлов.
8. Защита от ботов — слои: admission control до загрузки, глобальные и персональные квоты,
   bounded queue, ограничения вычислений/диска, rate limits и self-hosted challenge.
   CAPTCHA/PoW в одиночку не решает задачу.

**Главное ограничение:** невозможно одновременно обещать произвольные 3MF, много параллельных
слайсеров, весь инфраструктурный стек и безопасную публичную работу на 4 GiB RAM.
Первый релиз на таком сервере — ограниченный пилот с `N = 1`, уменьшенным максимальным
файлом и обязательным ресурсным испытанием. Если оно не проходит — увеличиваем RAM,
а не отключаем изоляцию и не разрешаем swap вместо расчёта.

## 2. Подтверждённые требования и предположения

### 2.1. Подтверждено пользователем

- Публичный сервис, основной сценарий без регистрации.
- Регистрация необязательна; в аккаунте видны свои задачи и результаты.
- Первый сервер: ориентировочно 4 ядра и 4 ГБ RAM; production — Ubuntu, Docker.
- Гости: 24 часа хранения и возможность вернуться по ссылке.
- Зарегистрированные: пока без срока удаления пользовательских результатов.
- Очередь, позиция и оценка ожидания, ограниченный параллелизм, автомасштабирование по ресурсам.
- Хранилище исходников, результатов и диагностики; дедупликация по хешу.
- Человекопонятные имена выходных файлов, JSON/log только в debug-режиме UI.
- PostgreSQL/Flyway/JPA — выбранный стек при использовании БД.
- RabbitMQ и MinIO были предложены как варианты, а не как неизменяемое требование.
- До реализации нужен анализ и зафиксированная спецификация.

### 2.2. Предложения, требующие утверждения

- `compact` использует PostgreSQL queue; RabbitMQ включается профилем `standard`.
- SeaweedFS — кандидат вместо неподдерживаемого MinIO; окончательное принятие после S3-тестов.
- Бессрочность относится к входам, готовым 3MF и бизнес-отчётам, но не к debug-логам/scratch.
- Конкретные квоты и таймауты ниже — стартовая политика, а не измеренные пределы сервера.
- Первый поддерживаемый production target — Ubuntu LTS **x86-64**. ARM64 — после отдельной
  проверки слайсеров. Размер SSD и необходимость бэкапа ещё не заданы.
- Нужны домен/TLS, способ доставки писем и политика восстановления аккаунта. Отсутствие
  SMTP не должно блокировать гостевой сценарий, но нельзя обещать email-восстановление без него.

это **не** время полного задания: слайсинг, подготовка, проверка и schedule-benchmark остаются.
ETA и resource sizing нельзя считать по одному `pack_footprint`.

## 4. Архитектура и границы компонентов

### 4.1. Основные компоненты

- **Gateway**: TLS, React static files, `/api`, ограничения HTTP, маршрутизация закрытой S3
  выдачи. Снаружи открыт только HTTPS; административные интерфейсы не публикуются.
- **API/control plane**: текущий Kotlin/Spring проект. Авторизация, владельцы, квоты,
  upload sessions, API задач, планировщик очереди, выдача ссылок, retention и recovery.
  Native слайсер внутри этого JVM не запускается.
- **PostgreSQL**: единственный источник истины о состоянии и доступе. Файлы в bytea не храним.
- **Object storage**: приватное S3-совместимое хранилище с постоянным Docker volume.
- **Node agent**: один доверенный лёгкий supervisor на execution-хост. Регистрирует
  доступный бюджет, получает назначения, создаёт sandbox runner, переносит вход/выход,
  следит за heartbeat, deadline, cgroup и отменой. Рекомендуемый вариант — отдельный Rust
  binary в существующем workspace, без второй тяжёлой Spring JVM на compact-хосте.
- **Runner**: короткоживущий контейнер на одну попытку: Rust CLI + закреплённый slicer runtime.
  Никаких общих HOME/config/workdir между пользователями. Не имеет DB/S3/Rabbit credentials.
- **RabbitMQ**: опциональный транспорт назначения в `standard`. Не хранит 3MF, не определяет
  владельцев, TTL файлов и позицию пользователя в очереди.

Control plane остаётся модульным приложением, а не набором произвольных микросервисов.
Kubernetes, Redis, отдельный Keycloak и тяжёлый observability stack не нужны для первого сервера.

### 4.2. Путь задачи

1. Получить гостевую/пользовательскую сессию и пройти admission control.
2. Зарезервировать upload quota; принять файл потоком, посчитать SHA-256, положить в quarantine.
3. Ограниченно проверить ZIP/метаданные; завершить загрузку и создать владельческую ссылку на blob. Проверка метаданных имеет отдельный bounded pool (в compact — 1),
   лимиты CPU/памяти/чтения и не запускает слайсер; глубокая native-проверка — уже в runner.
4. Создать задачу с idempotency key, заморозить параметры/профиль; транзакционно поставить в очередь.
5. Dispatcher назначает свободный execution slot, создаёт попытку с fencing token.
6. Node agent получает назначение, скачивает input в ограниченный scratch, запускает runner.
7. Runner последовательно выполняет probe/packing/slicing/verification либо schedule workflow.
8. Agent выгружает результаты и manifest; API транзакционно фиксирует успех текущей попытки.
9. UI получает результат и короткую авторизованную ссылку на объект. Scratch удаляется.
10. Retention/GC удаляет логические ссылки и физические объекты по правилам ниже.

В первой версии одна queue job — **весь pack или весь schedule**, а не отдельная внутренняя
нарезка. Это сохраняет контракт текущих CLI. Внутренний параллельный запуск каждого sample
не добавляем: он обошёл бы общий лимит `N`. Дробление schedule на дочерние задачи — отдельное
улучшение, если измерения покажут необходимость справедливого вытеснения длинных jobs.

## 5. Очередь, надёжность и RabbitMQ

### 5.1. Очередь обязательна; RabbitMQ — нет

В `compact` worker запрашивает работу у внутреннего API каждые 2 секунды только при наличии
свободного слота. API короткой транзакцией выбирает подходящую задачу, резервирует slot и
возвращает assignment. Повтор claim после потери HTTP-ответа идемпотентен по
`node_id + boot_id + slot_id`: возвращается существующее назначение, не создаётся второе. SQL использует row locks/`FOR UPDATE ... SKIP LOCKED`; PostgreSQL
документирует этот механизм как подходящий для queue-like tables [S5].

JPA используется для обычных entities/repositories. Claim, квоты, fencing и выборка GC могут
использовать native SQL в отдельном repository. Долгих JPA-транзакций на время слайсинга нет;
`ddl-auto=validate`, схема меняется только Flyway.

### 5.2. Политика выдачи

- Базово FIFO по `(enqueued_at, id)` среди подходящих задач.
- Не более одной выполняющейся задачи на владельца по умолчанию.
- Владельцы с исчерпанным лимитом пропускаются; нельзя занимать worker ожиданием их разрешения.
- При появлении нескольких слотов длинные schedule jobs имеют отдельный soft-cap; свободные
  слоты можно занимать ими при отсутствии коротких jobs, но начатую работу не прерываем.
- Квоты apply к атомарным admission reservations; проверки `count()` без блокировки недостаточны.
- Retry имеет `available_at`, не горячий цикл requeue. Защита от starvation — максимальное
  ожидание и наблюдение за возрастом старейшей задачи, а не скрытая постоянная приоритизация.
- Более сложный weighted-fair scheduler допустим позже; его включение должно менять и ETA.

### 5.3. Состояния

`QUEUED → DISPATCHED → RUNNING → FINALIZING → SUCCEEDED`

Альтернативы:

- `QUEUED/DISPATCHED/RUNNING/FINALIZING → CANCEL_REQUESTED → CANCELLED`;
- `DISPATCHED/RUNNING/FINALIZING → RETRY_WAIT → QUEUED` для разрешённых временных сбоев;
- `… → FAILED` для ошибок входа, unsupported profile, deadline, превышения ресурсов;
- `QUEUED/RETRY_WAIT → EXPIRED` при превышении максимального ожидания;
- `SUCCEEDED/FAILED/CANCELLED/EXPIRED → retention deletion` — отдельный процесс удаления данных.

Состояние удаления файлов не подменяет причину завершения job. Для авторизованного владельца
можно сохранить краткую tombstone «результат удалён», без рабочих файлов и секретов.

### 5.4. Lease и fencing

- Каждое назначение получает `attempt_id`, возрастающий `fence`, `node_id`, `boot_id`, `slot_id`.
- Heartbeat, например, раз в 10 секунд, lease — 60 секунд; числа настраиваются.
- Progress/finalize/cancel acknowledgement принимаются только от текущей попытки и fence.
- Старый worker не может опубликовать успех поверх новой попытки. Его объекты остаются
  attempt-scoped orphan objects и убираются GC.
- При потере control plane агент прекращает новые запуски; после grace period завершает
  runner, если не может продлить lease. Lease в БД сам по себе не убивает ОС-процесс.
- Слот нельзя считать физически свободным, пока агент/runtime не подтвердил остановку
  контейнера. Недоступный execution node исключается из доступной мощности, а не считается
  свободным. Замена такого node не должна двойным счётом увеличить host budget.
- Reconciler находит зависшие DISPATCHED/lease-expired попытки и выполняет recovery.
- Автоповторов по умолчанию один; повторные OOM, невалидный ZIP и невозможная геометрия
  не запускаются бесконечно с тем же бюджетом.

### 5.5. Профиль с RabbitMQ

Рекомендован после перехода на больший хост/несколько execution nodes, либо если его эксплуатация
уже решена. Состояния и планирование остаются в PostgreSQL, меняется **транспорт assignment**:

- В одной SQL-транзакции создаются DISPATCHED attempt, reservation и **outbox event**.
- Outbox publisher отправляет небольшой JSON `{jobId, attemptId, fence, nodeId, slotId, schemaVersion}`.
  Использует publisher confirms и mandatory routing; отсутствие маршрута не считается доставкой.
- Node agent принимает команду с manual ACK и небольшим prefetch (1 на слот). ACK выдаётся
  после долговременного подтверждения/claim в БД через internal API, **не после многочасового
  слайсинга**. ACK здесь значит «назначение принято», а не «job успешно выполнен».
- Повторная доставка той же попытки идемпотентна: дополнительный runner не запускается.
- После ACK выполнение защищают DB lease/reconciler. Без них ранний ACK был бы потерей задач.
- `prefetch=1` не заменяет admission slots: после раннего ACK consumer может принять следующую
  команду. И dispatcher, и agent проверяют занятость slot и fence.
- Durable queues, persistent messages, bounded retry/DLQ, versioned schemas. Тип quorum queue
  и конкретная версия RabbitMQ фиксируются при развёртывании. Один broker на одном диске не HA;
  несколько replicas на том же хосте не дают устойчивости к потере хоста.
- Нет distributed transaction PG↔RabbitMQ: outbox + идемпотентность закрывают этот разрыв [S6].

Причина отдельного ACK-дизайна: у RabbitMQ документирован default acknowledgement timeout
30 минут; особенности его применения зависят от типа очереди/версии [S7]. Простая схема
«держать unacked, пока slicer не закончит» без согласованных deadline здесь ненадёжна.

**Не делаем две независимые очереди:** RabbitMQ не решает, какая задача следующая, отдельно
от БД. При недоступном broker задания остаются QUEUED/DISPATCHED и восстанавливаются через outbox;
не переключаем транспорт автоматически посреди исполнения без согласованного fence.

## 6. Автоподбор ресурсов и предел параллельности

### 6.1. Что именно масштабируется

Количество API-потоков, consumers, worker controllers и native runners — разные величины.
Один agent способен контролировать `N` отдельных runner containers. Не нужно запускать
полноценную JVM на каждую задачу. Масштабируем native slots; существующий слайсер уже может
создавать много потоков внутри одного процесса.

`N` — общий предел активных native workflows на execution-host. Для нескольких hosts:
`N_cluster = min(operator_cluster_cap, sum(healthy_node_admitted_slots))`.
Бюджеты двух agents одного физического host нельзя суммировать как независимые.

### 6.2. Вычисление

Host-side bootstrap `deploy/up --auto` (будет реализован) определяет эффективные ресурсы,
сохраняет читаемый sizing report и генерирует deployment overrides. В контейнере нельзя
слепо использовать host CPU count или `/proc/meminfo`, игнорируя cgroup limits.

Учитываются CPU affinity/cpuset, quota/period, memory limit и operator budget; на Docker Desktop —
ресурсы Linux VM. Ресурсы самого маленького agent-container не принимаются за бюджет всей машины.
Bootstrap передаёт agent уже выделенный execution budget; тот может только уменьшать admission.

Формула для одного resource class:

`N = max(0, min(N_operator, floor(C_execution / C_job), floor(M_execution / M_job), floor(D_scratch / D_job)))`

- Используются фактически доступные байты, не надпись «4 GB» в тарифе: GB и GiB могут различаться.
  Из общих ресурсов сначала вычитаются ОС, API, PostgreSQL, S3, RabbitMQ (если включён),
  agent и аварийный запас. Persistent storage и scratch считаются раздельно, даже на одном SSD.
- Если `N = 0`, система сообщает «недостаточно ресурсов» и не делает вид, что безопасен `N = 1`.
- CPU/RAM/PID/scratch hard limits реально выставляются runtime. Docker-контейнеры без
  специальных настроек ресурсами не ограничены [S8].
- `RAYON_NUM_THREADS` ограничивает Rust pool, driver проверяет поддержку thread limit у
  конкретного slicer. Авторитетный ограничитель всего дерева процессов — cgroup, а не env.
- Peak RSS, CPU seconds, wall time и scratch bytes записываются для последующей калибровки.
- Повышение лимита выполняется после стабильных измерений и в пределах operator cap;
  снижение admission по memory/disk pressure не убивает уже работающие jobs без hard failure.
- Не оцениваем RAM только по размеру ZIP: число треугольников, supports, цвета и копии влияют сильнее.

### 6.3. Начальный профиль 4 vCPU / 4 GiB

Это **кандидат бюджета для P0-испытания**, а не доказанный production capacity plan:

| Компонент/резерв | RAM |
|---|---:|
| ОС, Docker и аварийный запас | 768 MiB |
| API/control plane JVM, включая native overhead | 512 MiB, heap не более 256–320 MiB |
| PostgreSQL | 384 MiB, небольшой pool/connection cap, tuned shared_buffers/work_mem |
| S3 single-node | 512 MiB |
| Node agent | 128 MiB |
| Gateway | 64 MiB |
| Один runner, всё дерево native processes | 1536 MiB |
| Итого | 3904 MiB |

В этот бюджет **не входит RabbitMQ**. Даже он оставляет мало свободной памяти; если выбранный
S3/слайсер требует больше, профиль не принимается. Swap не учитываем как RAM для параллелизма.
Не делаем обещания нарезать любой загружаемый 50 MiB ZIP в 1536 MiB RAM.

Старт: `N_max=1`, `job_cpu=2`, `job_memory=1536MiB`, `MAX_UPLOAD=50MiB`, `MAX_SCRATCH_PER_JOB=2GiB`.
Диск неизвестен: public mode требует явно заданный `STORAGE_BUDGET_BYTES` и положительный
остаток под images, БД/WAL, backups и scratch. Автодетект free disk не означает, что можно
занять весь раздел объектами.

Для `standard` примеры CPU/RAM **execution pool после вычета инфраструктуры**:

| Execution pool | Бюджет job | Результат расчёта |
|---|---|---|
| 4 CPU / 4 GiB | 2 CPU / 4 GiB | 1 |
| 6 CPU / 10 GiB | 2 CPU / 4 GiB | 2 |
| 12 CPU / 24 GiB | 2 CPU / 4 GiB | 6, если допускают диск и operator cap |

Это иллюстрации формулы, не обещание такой доступной памяти на VPS соответствующего размера.
Если несколько задач быстрее заканчиваются при 2×2 CPU, чем 1×4 CPU, выбираем первое после
throughput-теста; количество пользователей само по себе не повод увеличивать `N`.

## 7. Слайсеры в Ubuntu/Docker

### 7.1. Как вызываются сейчас

Backend запускает Rust CLI. Rust берёт путь из `slicer_path` профиля и вызывает соответствующий
исполняемый файл. BambuStudio/OrcaSlicer не ищутся автоматически. В репозитории пути macOS.
CLI у BambuStudio документирован, у OrcaSlicer документирован headless mode [S2, S3];
у BambuStudio также есть Docker guide [S4]. Но это не доказывает совместимость именно нужной
версии, модели/опор и окружения этого проекта.

### 7.2. Предлагаемый runtime contract

- Printer profile содержит геометрию/ограничения и `slicer_kind`, но не произвольный executable
  пользователя. Runtime registry связывает kind с разрешённым image digest и driver.
- При создании job фиксируются profile snapshot/hash, версия пакера, slicer/version/image digest,
  архитектура CPU и нормализованные параметры. Обновление профиля не меняет уже стоящую задачу.
- Separate runners: `runner-bambu:<pinned>` и `runner-orca:<pinned>`; в compact можно держать
  оба образа на диске и запускать только требуемый контейнер, а не два постоянно живых GUI.
- Image build устанавливает все shared libraries, locale/fonts и slicer resources; выполнение
  не скачивает профили, плагины, обновления или принтерные cloud-компоненты.
- Driver проводит startup smoke: version/help, минимальный 3MF, ожидаемый G-code/result.json,
  корректный exit code. Проверяется необходимость Xvfb/software rendering; если нужен Xvfb,
  он внутри runner, входит в его бюджет, без mount host X11 и без privileged mode.
- Не требуем GPU на первом сервере. Не обещаем, что произвольный CLI build не использует графику.
- AppImage при необходимости распаковывается во время сборки, без runtime FUSE/privileged.
- Сохраняем различия Bambu/Orca в отчётах и уже существующие адаптации профилей. Не заменяем
  один слайсер другим только потому, что оба принимают 3MF.
- Проверяем лицензии и возможность поставки выбранных binaries/resources в образе.
  Документируем исходники/notice и обязанности для выбранной сборки; не считаем свободный
  download автоматическим разрешением на любую перепаковку. Конкретный legal review — release gate.

### 7.3. Изоляция недоверенного ввода

Native parser/slicer — наиболее рискованная граница: пользователь загружает сложный ZIP/XML/mesh.
В runner:

- отдельный непривилегированный UID, read-only root filesystem, dropped capabilities,
  `no-new-privileges`, ограниченные CPU/RAM/PIDs/file descriptors;
- `network=none`, никаких Docker socket, БД, S3 secrets, home администратора или host X11;
- input read-only, отдельный scratch/output с лимитом; никаких общих пользовательских configs;
- deadline на попытку и стадии; cancel/timeout завершает контейнер и всё дерево процессов;
- uploads не могут задавать команды, environment, image, mounts или пути profiles;
- запрещены внешние ссылки/XXE, traversal, symlink extraction, encrypted ZIP, бесконечные
  XML/ZIP bombs, исполнительные post-processing scripts из проекта. Если такие настройки
  обнаружены, понятная ошибка, а не скрытое изменение печатных параметров.

Agent — доверенный control boundary. Если он управляет Docker через socket, это мощное
полномочие, даже когда container называется «worker». Предпочтителен отдельный rootless
execution daemon; агенту разрешён только заданный набор images/mount roots/limits.
**API и runner никогда не получают Docker socket.** Администратор agent/runtime — доверенный
оператор. Доступ к agent только внутренний, а его API не принимает произвольный Docker JSON.

Дисковые лимиты не заменяются одним Docker volume: для scratch нужен filesystem quota/
выделенный ограниченный раздел/поддерживаемый runtime storage limit; простой опрос `du`
лишь дополнительный guard. Не помещаем большой scratch в tmpfs на 4 GiB сервере.

## 8. Позиция в очереди и ETA

### 8.1. Контракт UI

У QUEUED job отдаём:

- `queuePosition`, `eligibleAhead`, `queueScope`, `observedAt`;
- `estimatedStartFrom`, `estimatedStartTo`, `confidence: low|medium|high`, `estimateReason`;
- `blockedBy: capacity|owner_limit|runtime_unavailable|maintenance|null`;
- `expiresAt`, если есть конечный срок доступности/ожидания.

Пример UI: **«Сейчас вы 4-й среди ожидающих этого пула. Начало примерно через 6–12 минут»**.
Если данных нет: **«Вы 4-й. Время ожидания пока неизвестно»**. Если нет совместимого runtime:
не показываем «0 минут», а сообщаем о недоступном исполнителе.

Позиция — снимок порядка scheduling, не обещание неизменного FIFO: отмена, retry, per-owner
limit и доступные slicer capabilities меняют его. Приоритет/политика должны быть видимы,
а не создавать ложную «точную очередь». Выдаём числа, не сведения о чужих файлах/владельцах.

### 8.2. Расчёт

- Источник порядка — БД и тот же scheduler selector. Счётчик RabbitMQ не учитывает running,
  reserved, delayed retries и ограничения владельца, поэтому для позиции не годится.
- История wall time всего job группируется по kind, slicer/version, resource class,
  диапазону геометрической сложности/объектов и режиму adaptive/full.
- Для текущих jobs оценивается остаток по завершённым стадиям; одинаковые стадии используются
  в logs/progress/ETA. Никакого линейного процента по числу байт ZIP.
- Симулируем назначение ожидающих задач на освобождающиеся slots с теми же ограничениями;
  вычисляем optimistic/conservative estimate по наблюдаемым распределениям.
- Используем сглаженные медианы/перцентили только при достаточной выборке. На cold start —
  диапазон с low confidence или null, не выдуманные секунды.
- Пересчёт после enqueue/start/finish/cancel и не чаще разумного интервала; UI poll 5 секунд
  во время работы, 10–15 секунд в очереди, backoff при ошибках, остановка на terminal/410.
  SSE можно добавить позже с connection limits; не нужен отдельный event-broker для первого UI.

## 9. Владельцы, гостевые ссылки и регистрация

### 9.1. Гости

Первое посещение создаёт случайную серверную guest identity и HttpOnly Secure SameSite cookie.
Все upload intents, файлы и jobs имеют owner. IP — сигнал rate limit, **не идентификатор владельца**.
Перезапуск backend не теряет сессии/права: метаданные хранятся в БД.

Возвратная ссылка: `https://service/jobs/<uuid>#access=<random-256-bit-token>`.

- UUID используется для маршрута, token — bearer capability для чтения **одной** задачи.
- В БД хранится хеш токена; токен не включается в логи, аналитику и Referer.
- Фрагмент frontend один раз обменивает через HTTPS на ограниченную сессию; очищает fragment
  из адресной строки. Страница без third-party analytics, `Referrer-Policy: no-referrer`, CSP.
- Ссылку можно скопировать/сохранить. Кто получил её, может прочитать разрешённый результат;
  это должно быть написано в UI. Потерянную гостевую ссылку без сессии восстановить нельзя.
- Read capability не даёт delete/cancel/claim ownership. Эти действия требуют исходную guest
  session либо владельца аккаунта и CSRF-защиту.
- Авторизованный владелец после expiry получает 410; посторонний без capability — 404,
  чтобы не раскрывать существование задачи.

### 9.2. Аккаунты

- Аккаунт не обязателен для запуска. После регистрации гостевая сессия может присоединить
  свои ещё живые задачи транзакцией; одного чужого read URL для claim недостаточно.
- Авторизация на Spring Security без отдельного identity server в compact. Sessions в БД,
  безопасное хеширование паролей, login/signup/reset rate limits, CSRF, logout/revocation.
- Email verification и reset требуют настроенной почты. Без подтверждения email/другого
  доверенного сигнала регистрация даёт историю, но не повышенные вычислительные квоты.
- При claim гостевой read-token отзывается; владелец входит через аккаунт, при желании создаёт
  новую ограниченную share link. Уже удалённые по TTL файлы не «воскресают».
- «Мои задачи»: пагинация, фильтры kind/status, дата, параметры, output, bytes/quota,
  ссылки на повтор с другими параметрами. Никаких общих публичных списков jobs.
- Delete account/jobs удаляет логические ссылки и инициирует GC; правила и задержка удаления
  бэкапов явно описаны. Бессрочное хранение не равняется резервному копированию или SLA.

## 10. Объектное хранилище, имена, TTL и GC

### 10.1. S3 provider

SeaweedFS предоставляет S3 и single-node режим `weed mini` [S9]. Выбор принимается только после
проверки pinned image: PUT/GET/HEAD/DELETE, streaming upload/abort, range, presigned GET,
Content-Disposition, restart persistence, storage limits, GC/compaction и backup/restore.
Не требуем всей AWS S3 API и не используем специфические lifecycle tags как ядро бизнес-логики.

MinIO-compatible endpoint может остаться поддержанным адаптером. Если нужен именно MinIO,
отдельно выбираются поддерживаемая поставка/лицензия и operational policy; старый public
`latest` image не фиксируется как долгосрочная production-зависимость.

S3 тоже физически хранит данные на диске. Улучшение относительно `/tmp` — устойчивое
хранилище, права, разделение metadata/data, общий доступ workers, управляемая очистка,
а не исчезновение диска и эксплуатационных обязанностей.

### 10.2. Ключи и имена

Внутренние keys не строятся из пользовательского имени:

- `quarantine/<uploadId>/source`;
- `blobs/sha256/<prefix>/<digest>/<generation>`;
- `jobs/<jobId>/attempts/<attemptId>/outputs/...`;
- `jobs/<jobId>/attempts/<attemptId>/debug/...`;
- immutable manifest завершённой попытки со ссылками на input/output/profile/diagnostics.

Готовый download filename: **`cat_p1s_40_packed.3mf`**.

- Base name берётся из metadata исходного file record; удаляются path separators, CR/LF,
  control chars, опасные/служебные имена, длина ограничивается; пустое имя заменяется `model`.
- `p1s` — явный стабильный `downloadSlug` профиля, а не эвристическое обрезание любой строки.
- `40` — подтверждённое итоговое количество, не запрошенный максимум.
- В `Content-Disposition` передаётся безопасное UTF-8 filename; user name никогда не путь runner.
- Объектные keys уникальны независимо от одинаковых имён скачивания.
- Для schedule: `cat_p1s_63_schedule.3mf`, CSV/XLSX с тем же base. Можно хранить внутренние
  CLI-имена `packed.3mf`/`plates.3mf`, не ломая контракты сборщика.

### 10.3. Выдача

API проверяет владельца/capability, состояние и TTL, затем выдаёт короткий signed GET,
например на 5 минут и не дольше остатка retention. Скачивание идёт из storage через HTTPS
storage endpoint/gateway, не из локального `/tmp` API.

Bucket private, list запрещён, административный UI только во внутренней сети. Signed URL —
секрет; не логировать query string. Ссылка, уже выданная до удаления, может работать до её
короткого истечения — мгновенную отзывность direct S3 URL не обещаем. Если нужна немедленная
отзывность, применяем авторизованный download proxy вместо прямой presigned выдачи.

### 10.4. Сроки

| Данные | Гость | Аккаунт |
|---|---|---|
| Незавершённый upload intent | 15 минут | 15 минут |
| Готовая загрузка без job | 24 часа после загрузки | До удаления/квоты, без срока |
| Input, связанный с живой job | Pin до terminal/deadline | Pin до terminal/deadline |
| Input/output готовой job | 24 часа после terminal | Без автоматического TTL, в пределах квоты |
| Бизнес-отчёты CSV/XLSX | Как output | Как output |
| Debug JSON/log | До guest expiry | Предложение: 7 дней |
| Scratch runner | До finalize/ошибки, затем немедленная очистка | То же |
| Orphan output/quarantine | Короткий grace, затем GC | То же |

Это уточнение «24 часа»: гость получает 24 часа **на скачивание после окончания**, а не
теряет результат, если очередь заняла большую часть срока от загрузки. Неиспользуемая
загрузка живёт 24 часа от upload. Активные jobs ограничены max queue wait и wall timeout,
поэтому pin не продлевается бесконечно. Привязка input к новой job создаёт отдельную
ссылку/retention, а не бессрочно оживляет все старые ссылки.

### 10.5. Почему одной bucket lifecycle policy недостаточно

Lifecycle по возрасту объекта не знает, что этот blob одновременно нужен гостю, аккаунту,
retry и запущенному schedule. Нельзя удалить shared blob через 24 часа от первого PUT.

- Источник истины — file references, nullable `expires_at`, активные input pins и attempts.
- GC сначала логически истекает ссылки, затем под блокировкой помечает blob без живых ссылок
  `DELETE_PENDING`, выполняет идемпотентный S3 DELETE и фиксирует удаление.
- Новая ссылка не может прицепиться к уже удаляемой generation. При гонке upload создаёт новую
  generation/восстанавливает объект отдельной процедурой, а не надеется на `HEAD → attach`.
- Ошибка S3 DELETE повторяется; rollback удалённого физического объекта не притворяется возможным.
- Provider lifecycle полезен как страховка для незавершённых multipart/quarantine, но не
  заменяет DB-aware GC общих blobs.
- Освобождение места на физическом диске может требовать compaction; admission смотрит и
  logical reservations, и actual free space, оставляя запас для compaction/WAL.

## 11. Дедупликация, идемпотентность и кэш — разные задачи

1. **File dedup:** SHA-256 точных байтов потоком на сервере + размер. S3 ETag не считаем
   SHA-256 и не используем как универсальный digest, особенно для multipart.
2. **Ownership:** физический blob может быть один, file records/права/retention раздельные.
   Владелец платит своей логической квотой за файл даже при глобальной экономии физических байтов.
3. **Upload race:** временные upload keys, атомарная DB unique/lock процедура finalize, immutable
   final generation, уборка проигравшей копии. Одновременные upload не оставляют постоянные дубли.
4. **Privacy:** клиентский digest — только подсказка, не доказательство владения. Не отдаём
   чужой файл по знанию хеша и не раскрываем endpoint «существует ли такой файл у кого-нибудь».
   До пропуска upload возможен поиск только среди доступных этому owner живых файлов.
   Для межпользовательского dedup сначала принимаем и проверяем байты.
5. **Job idempotency:** повтор одного POST/timeout с тем же `Idempotency-Key` и payload возвращает
   ту же job. Другой payload с тем же key — 409. Один файл с разными настройками — законные jobs.
6. **Result cache (после MVP):** отдельный fingerprint из input hash, полного profile snapshot,
   нормализованных параметров, slicer/packer versions и resource/architecture policy.
   Кэш owner-scoped по умолчанию, только живые проверенные успешные результаты.
   Авто-«семантическую дедупликацию» моделей по форме не делаем: paint/settings/metadata значимы.

Таким образом hash dedup защищает диск, но сам по себе не защищает CPU и повторную очередь.

## 12. Безопасность и защита от 10 000 ботов

### 12.1. Границы обещаний

На одном небольшом сервере нельзя гарантировать доступность для всех легитимных гостей
при большой распределённой атаке. Можно и нужно гарантировать: очередь и storage bounded,
CPU/RAM не растут бесконечно, отказ быстрый/понятный, выполняющиеся jobs не вытесняются
мусорными запросами. При saturation новые запросы получают 429/503 + Retry-After.
Внешняя сетевая DDoS-защита — отдельный вопрос хостинга; локальная CAPTCHA канал не защищает.

### 12.2. Защита до записи байтов

- Gateway: request/body/header size, upload timeout/minimum throughput, per-IP и global
  request/connection caps. Доверять X-Forwarded-For только своему proxy, не клиентскому заголовку.
- API выдаёт ограниченный одноразовый upload intent после проверки owner/IP/global quota и
  challenge. Резервирует заявленный размер; проверяет фактические байты, обрывает превышение.
- Идёт **streaming**, не `readBytes()` на весь файл. Для compact upload через контролируемый
  backend endpoint проще защищать, чем раздавать гостям неограниченные S3 PUT.
- Если позже используются presigned uploads, только конкретный key, короткое время,
  подтверждённые лимиты размера/provider POST policy, reservation, finalize и GC. Пересылка
  одной presigned ссылки не должна давать неограниченное количество новых объектов.
- Bounded validation pool; metadata read limits; archive entry count и total uncompressed size,
  limits на одну XML/config entry, допустимые compression methods/paths. Проверка расширения
  файла — не проверка 3MF. Native parsing только в sandbox.

### 12.3. Anti-bot challenge

Кандидат — self-hosted ALTCHA proof-of-work: challenge создаётся и проверяется сервером [S10].
Скрипт widget включается в наш frontend bundle, не с внешнего CDN. Server проверяет подпись,
срок, сложность, single-use nonce и привязку к upload/job intent. Нельзя ограничиться наличием
поля от клиента. Это добавляет стоимость ботам, но не подтверждает личность и не заменяет квоты.

Для accessibility/слабых устройств — понятный повтор/альтернативный подтверждённый аккаунт;
не повышаем сложность до непригодности для телефона. Challenge выдаётся до дорогой загрузки,
его endpoint тоже rate-limited. Подозрительный трафик получает более строгие лимиты, а не
приоритет за большое число успешно решённых challenges.

### 12.4. Стартовая политика `compact` — все числа конфигурируемы

| Ограничение | Предложение |
|---|---|
| Одновременно heavy jobs глобально | 1; дальше resource formula |
| Ожидающие jobs глобально | 20, включая delayed retries/reservations |
| На гостя | 1 running + 1 queued; короткий job-submit cooldown |
| На аккаунт | 1 running + 3 queued; не повышать лимит простой массовой регистрацией |
| Upload одновременно | 2 глобально, 1 на owner |
| Максимальный upload | 50 MiB compact, standard — до 200 MiB после испытаний |
| Guest logical storage | 150 MiB; input + output + diagnostics учитываются/резервируются |
| Account logical storage | 1 GiB и максимум 100 сохраняемых results как стартовый тариф |
| Global storage | Явный operator budget, ограниченный фактическим диском и резервами |
| Queue wait | 2 часа, затем EXPIRED, с явным сообщением |
| Native wall deadline | 30 минут guest; до 90 минут account, после проверки сценариев |
| Повтор временного сбоя | 1, с backoff; не повторять тот же OOM автоматически |
| Полный schedule benchmark | По умолчанию выключен для гостя, adaptive + лимит внутренних samples |
| Diagnostics | Ограниченные bytes/attempt и retention; не бесконечные raw logs |

Предварительные суточные defaults: guest и неподтверждённый аккаунт — до 4 новых jobs и
60 минут native wall time; подтверждённый аккаунт — до 10 jobs и 180 минут. Это два
одновременных ограничения: 4 jobs не дают права на 4 × максимальный timeout при исчерпанном
compute budget. На guest IP/network — начальный дополнительный throttle 10 submissions/сутки;
для общей NAT-сети нужны понятное сообщение и переход к подтверждённому аккаунту, не ложная
привязка чужих файлов к IP. Сетевые rate limits действуют также на signup/challenge/download.

Глобальный предлагаемый compute ceiling — 20 slot-hours в сутки на каждый утверждённый
execution slot (не более operator cap), плюс backlog work budget около 2 slot-hours на слот.
Это ограничивает принятую тяжёлую работу, а не обещает throughput. На cold start backlog cost
считаем консервативно, после измерений — по истории и uncertainty margin. Фактические CPU
seconds учитываются отдельно от wall time; idle/deadline нельзя использовать для обхода.
Quota reservations/settlement обеспечивают эти пределы конкурентно; перед запуском ещё раз
проверяется оставшийся бюджет. Infrastructure retry не увеличивает пользовательский счётчик
новых jobs, но потреблённые ресурсы не исчезают из глобального учёта.

Все эти числа подлежат P0 throughput/abuse measurement и утверждению перед публичным запуском.
Они предложены как закрывающие систему безопасные defaults, не как доказанная полезная ёмкость
сервера. Ограничение только числом задач без учёта длительности недостаточно.

IP/NAT не является надёжной идентичностью: используем его для throttling, не для доступа к
файлам. Ограничение аккаунта без ограничения регистраций/глобального бюджета также обходится.
При атаке допустим режим «новые гостевые задачи временно закрыты», без потери уже принятых.

Квоты считаются **до** admission, с транзакционными reservations для uploads, outputs и scratch.
Лимит после заполнения диска бесполезен. Превышение output-size завершает job понятной ошибкой,
не оставляет частичный файл с SUCCEEDED. Повторное чтение/скачивание имеет bandwidth/rate limits.

## 13. Логи, прогресс и `?debug=true`

### 13.1. Пользовательский контракт

- Обычный pack: итоговый 3MF, число деталей, профиль, длительность, статус/срок хранения.
- Обычный schedule: 3MF + CSV/XLSX как полезные бизнес-результаты.
- `?debug=true`: дополнительно sanitized logs, placements/verification/report JSON,
  версии/runtime summary, диагностический preview. `false`/другие значения не включают режим.
- Это флаг **представления, не авторизация**. API `includeDebug=true` всё равно проверяет
  owner/capability и доступ к конкретным артефактам. Даже скрытый endpoint защищён.
- Raw sensitive/operator logs не выдаются гостевым capability; обычные диагностические
  материалы очищены от secrets, абсолютных host paths и чужих идентификаторов.
- При FAILED обычный UI показывает error code, стадию и понятное действие. Stack trace —
  не основной текст. Retry button создаёт контролируемый запрос, не обходящий admission.

### 13.2. Структура событий

Общий envelope: `timestamp UTC`, `level`, `service`, `event`, `request_id`, `job_id`,
`attempt_id`, `fence`, `node_id`, `phase`, `duration_ms`, `error_code`; payload versioned.

События: upload accepted/rejected, checksum verified, duplicate reused, job queued/claimed,
resource reservation, runner started, slicer version/stage started/finished, heartbeat,
packing candidate summary, result verified, artifact uploaded, cancel, deadline/OOM,
retry scheduled, terminal state, expired reference, GC completed/failed.

Rust вводит structured log mode (например через tracing) и стабильные progress events.
Человеческий CLI-режим сохраняется. Backend больше не выводит бизнес-состояние только
из случайных regex по английским фразам. Для legacy binary regex adapter остаётся временно.

`Command.output()` заменяется streaming subprocess supervision: одновременно читать stdout
и stderr, не допускать pipe deadlock, ограничивать строку/общий объём, получать exit status,
deadline и resource usage. Записи child process добавляются к job log с `component=slicer`
или `component=packer`, а ключевые milestones зеркалируются в backend/agent structured logs.
Не копировать каждую шумную строку всех слайсеров в API INFO без ограничения.

### 13.3. Где хранить

- Console JSON logs каждого сервиса с rotation/size cap у runtime.
- Job logs: bounded локальный spool, chunk upload в S3 раз в 10–30 секунд/по размеру,
  final manifest и сжатый итог. Не один S3 PUT и не одна DB insert на каждую строку.
- Прогресс хранится в компактном DB snapshot; milestones — job_events. Tail API ограничивает
  bytes/строки/частоту. Worker crash может потерять последний незагруженный chunk — это
  явно известное диагностическое окно, не потеря durable job state.
- Секреты, capability tokens, presigned query, пароли, SMTP credentials, 3MF bytes не логируются.
- Метрики: queue depth/age, active slots, wait/run percentiles, errors/retries/OOM, RSS/scratch,
  object bytes/reservations, expired pending GC, upload rejects, challenge failures.

## 14. Модель PostgreSQL

Ниже логические сущности, не окончательный DDL:

| Таблица | Основное назначение |
|---|---|
| `principals` | guest/account owner, policy class, quotas/status |
| `users`, `auth_sessions` | аккаунты, password/auth state, безопасные сессии |
| `access_capabilities` | хеш scoped read-token, job, expiry/revocation |
| `upload_sessions` | intent, owner, reservation, expected/actual bytes, state, expiry |
| `blobs` | SHA-256, size, storage key/generation, state, physical bytes |
| `files` | owner reference к blob, display name, purpose, expiry, deletion state |
| `jobs` | owner/kind/state/queue order, source, params, profile/runtime snapshots, timestamps, version |
| `job_attempts` | attempt/fence/node/slot/boot, lease/deadline, exit/error/resource statistics |
| `artifacts` | job/attempt/file/purpose, public/debug exposure, checksum/size |
| `worker_nodes`, `worker_slots` | capabilities, budgets, heartbeat, reservations |
| `quota_reservations`, `usage_counters` | конкурентно безопасные bytes/jobs/compute budgets |
| `job_events` | ограниченные milestones, не вся телеметрия и не raw output |
| `outbox_events` | доставка команд при RabbitMQ и прочих внешних событиях |

Инварианты БД:

- не более одной текущей исполняемой попытки на job, monotonic fence;
- slot не принадлежит двум живым attempts; owner/global квоты резервируются в той же транзакции;
- idempotency key уникален в owner scope и связан с payload hash;
- blobs дедуплицируются с учётом generation/state, а не только бессмысленным filename;
- итоговые артефакты опубликованы одной winning attempt; SUCCEEDED только после проверенного manifest;
- индексы owner+created, status+available_at+queue order, lease expiry, file expiry, blob references;
- optimistic version/CAS для status updates, короткие pessimistic/native SQL операции для claims/GC.

Flyway запускается выделенной migration job до API. Runtime DB user не имеет DDL permissions.
Бэкап/restore тестирует совместимость schema + object manifest, а не только наличие SQL dump.

Метаданные тоже ограничиваются: неиспользуемые guest sessions/upload intents/capabilities
удаляются по TTL, guest tombstones — например через 7 дней после expiry, technical events
следуют отдельному сроку. У аккаунта бессрочная видимая история хранится в пределах row quota
(предложение: 1000 jobs); достигнув её, пользователь удаляет старые записи или получает
увеличение квоты, а не теряет историю молча. Auth sessions имеют конечный TTL и максимум
на principal. Глобальные лимиты principal/job/event rows и размер WAL учитываются отдельно
от S3 bytes, чтобы миллион пустых регистраций не стал обходом object quota.

## 15. API следующей версии

Предлагаемые endpoints, окончательные DTO — на этапе implementation design:

- `POST /api/v2/guest-sessions` — гостевая сессия;
- `POST /api/v2/upload-intents` — admission/challenge/quota reservation;
- `PUT /api/v2/uploads/{id}/content` — bounded streaming upload;
- `POST /api/v2/uploads/{id}/complete` — проверка/finalize; повтор идемпотентен;
- `GET /api/v2/files/{id}` — metadata/inspection только своего файла;
- `POST /api/v2/jobs` — fileId, kind, options/profile selection, Idempotency-Key;
- `GET /api/v2/jobs/{id}` — state, phase, queue/ETA, summary, expiry;
- `GET /api/v2/jobs?cursor=...` — только свои, для аккаунта/текущей guest session;
- `POST /api/v2/jobs/{id}/cancel` — идемпотентная отмена, отдельно от удаления;
- `DELETE /api/v2/jobs/{id}` — удалить ссылки; active job сначала отменить/остановить;
- `GET /api/v2/jobs/{id}/artifacts?includeDebug=true` — авторизованный manifest;
- `POST /api/v2/artifacts/{id}/download` — короткий signed URL + безопасное filename;
- `POST /api/v2/capabilities/exchange`, auth/register/login/logout/claim-guest;
- internal node register/claim/heartbeat/progress/finalize API — отдельная аутентификация,
  network policy, никаких browser-accessible runtime controls. Node credentials scoped к
  собственным assignments; для нескольких хостов — mTLS/TLS. Agent не получает права
  произвольно менять чужой owner, скачивать все blobs или назначать себе больший ресурсный бюджет.

Статусы ошибок: 400 invalid format/params; 401/403 auth; 404 inaccessible/unknown;
409 idempotency/conflicting state; 410 expired для владельца; 413 upload limit;
429 owner/global admission quota с Retry-After; 503 capacity/runtime/storage unavailable.
Ни один из отказов не должен порождать полную native job или бесхозный upload без GC.

Миграция: старые multipart endpoints временно фасады над новыми сервисами, с той же owner
проверкой, лимитами и idempotency. Не оставлять публичный старый endpoint как обход защиты.

## 16. Docker и эксплуатация

### 16.1. Deployment profiles

`compact`: gateway + API/control + PostgreSQL + single-node S3 + lightweight node agent;
runner containers создаются по требованию. `standard` добавляет RabbitMQ/дополнительные agents.
Опциональный monitoring profile включается только если есть ресурсный бюджет.

- Ubuntu LTS + Docker Engine/Compose; версия и image digests зафиксированы, не `latest`.
- Multi-stage Rust/backend/frontend images; runtime не собирает зависимости и не обращается
  к registries. Для offline эксплуатации можно заранее загрузить все images/resources.
- Persistent volumes: PostgreSQL, S3 data/metadata; scratch отдельно, без общей папки jobs API.
- Health/readiness отдельно от liveness. API не принимает новую работу, пока нет миграций,
  storage write/read и хотя бы совместимого execution capability; историю отдавать можно.
- Secrets через Docker secrets/файлы с правами/операторский secret store, не в Git/images/logs.
- Agent runtime privilege boundary описан в §7.3. DB/Rabbit/admin/S3 console ports не наружу.
- Graceful shutdown: остановить claims, drain в пределах grace либо cancel→retry policy;
  не помечать live job успешной на остановке приложения.
- Runtime disk/log limits, DB WAL и object compaction reserves входят в расчёт диска.
- Single-host deployment имеет единые точки отказа; перезапуск переживается, потеря диска без
  бэкапа — нет. RabbitMQ и S3 на том же диске этого не исправляют.
- Нужен backup PostgreSQL + S3 metadata/data на другой носитель/хост, restore drill и
  retention бэкапов. До выбора места бэкапа формулировка — «best effort», не SLA бессрочности.

### 16.2. Конфигурационные группы

`DEPLOYMENT_MODE`, `QUEUE_TRANSPORT=postgres|rabbit`, `NODE_ID`, `EXECUTION_CPU_BUDGET`,
`EXECUTION_MEMORY_BUDGET`, `MAX_CONCURRENT_JOBS`, `JOB_CPU`, `JOB_MEMORY`, `JOB_SCRATCH_LIMIT`,
`RUNNER_IMAGE_ALLOWLIST`, `SLICER_RUNTIME_REGISTRY`, `LEASE_SECONDS`, `HEARTBEAT_SECONDS`,
`MAX_QUEUE_WAIT`, `JOB_TIMEOUT`, `MAX_RETRIES`, `MAX_UPLOAD_BYTES`, `MAX_QUEUED_GLOBAL`,
`MAX_QUEUED_PER_OWNER`, `MAX_UPLOADS_GLOBAL`, `STORAGE_BUDGET_BYTES`, `DISK_LOW_WATERMARK`,
`GUEST_RESULT_TTL=24h`, `ACCOUNT_RESULT_TTL=none`, `DEBUG_TTL`, `ACCOUNT_STORAGE_QUOTA`,
`SIGNED_URL_TTL`, `CHALLENGE_MODE`, auth/SMTP settings, trusted proxy origins, backup settings.

Все эффективные значения отображаются оператору и записываются при старте без secrets.
Пользователь API не может менять execution budgets, runtime images и глобальные TTL.

## 17. Критические сбои и ожидаемое поведение

| Сбой | Поведение |
|---|---|
| Повтор POST после сетевого timeout | Та же job по idempotency key |
| API упал после записи job | Очередь остаётся в PG; worker/reconciler продолжит |
| PG commit, но Rabbit publish не состоялся | Pending outbox повторит отправку |
| Publish состоялся, confirm потерян | Возможна повторная доставка, но не второй runner |
| Worker умер до/после ACK | Lease/recovery; ACK не критерий успеха |
| Старый worker закончил после retry | Fence отклоняет finalize, orphan output идёт в GC |
| Отмена во время финализации | Один CAS-победитель: успех уже зафиксирован либо отмена; UI не получает оба состояния |
| Storage упал после вычислений | Ограниченный FINALIZING retry; не пересчитывать всё без необходимости |
| Нельзя выгрузить результат до deadline | FAILED/STORAGE_ERROR, никаких ссылок на частичный output |
| Delete исходного pack, schedule уже принят | Job input pin/reference живёт независимо |
| Guest TTL совпал с началом job | Атомарный pin/claim; либо отказ expired, либо данные удержаны до deadline |
| Новый upload того же hash во время GC | Заблокирован attach к DELETE_PENDING; новая generation/повтор, без dangling refs |
| Storage заполнен | Приём закрывается до полного диска; существующие jobs имеют output/scratch reservations |
| Node потерял связь | Stop admission, grace, kill/fence; не считать недоступный слот свободным |
| Слишком тяжёлая модель/OOM | Ограниченный ущерб одному runner, понятная ошибка, без retry-loop |
| 10 000 новых guest identities | Глобальные лимиты/бюджеты удерживают очередь и диск; большинство запросов быстро отвергается |
| Зарегистрированный забил квоту без TTL | Новые uploads/jobs отклоняются; старые результаты не удаляются тайно |

## 18. План реализации и критерии приёмки

### P0 — обязательный compatibility/resource spike

До построения всей инфраструктуры:

1. Linux x86-64 images Bambu/Orca: проверка реальных P1S/U1/A2L fixtures, поддержек, цветов,
   башни, nozzle-clean, schedule workflow; actual slicing, не fake CLI.
2. Сравнение с текущими macOS результатами по геометрии/зазорам/артефактам; не требуем
   побайтно одинакового G-code между разными сборками без отдельного доказательства.
3. CPU/RSS/scratch/wall-time замеры на 4 GiB cgroup под конкурентными API/upload/download.
4. Проверка image dependencies, headless/Xvfb, thread caps, offline run и лицензий.
5. S3 compatibility/backup/restore/compaction probe на выбранном pinned SeaweedFS.
6. Утверждение SSD/storage budget и суточных compute quotas; выбор поддерживаемых версий
   Spring Boot/JDK/PostgreSQL и зафиксированных образов.

**Gate:** если полный compact budget и supported fixtures не проходят, увеличиваем RAM
или сужаем явно опубликованные ограничения. Не объявляем production готовым по fake-tests.

### P1 — durable foundation

Flyway, ownership/sessions, jobs/attempts/artifacts, storage abstraction, bounded uploads,
checksums/dedup/GC, простые quotas. Сохраняем работу текущих локальных CLI через adapter.
Проверка: API restart не теряет задачи; принятый файл не существует только в `/tmp`.

### P2 — isolated queue execution

PostgreSQL scheduling/leases/fencing, node agent, отдельные runner containers, resource
budgets, deadlines/cancel/recovery, publication manifest. Параллелизм сначала1.
Проверка: при нагрузке физически не больше `N` runner workflows, stale attempt не публикует результат.

### P3 — публичный UX

Guest capability links, optional registration/history/claim, position/ETA, имена результатов,
normal/debug artifacts, квоты/TTL в UI, понятные 429/503/410 и безопасные повторы.
Проверка: другой пользователь не видит чужие jobs/files/debug даже зная UUID/hash.

### P4 — abuse/load/operations gate

PoW/rate limits/compute quotas, malicious ZIP/XML fixtures, отказ storage/PG/worker, гонки
cancel/finalize/GC/dedup, quota-overflow, startup resource report, backups/restore.
Нагрузочный сценарий10k запросов тестировать на изолированном стенде, не на публичном VPS.
Проверка: bounded backlog/objects/reservations, жив API чтения, готовые файлы не теряются,
отказ не оставляет тысячи temp файлов и нескончаемых retries.

### P5 — standard/RabbitMQ и расширение

Включение Rabbit adapter/outbox/confirm/delivery recovery, более одного node/slot, ETA-калибровка.
Проверки duplicate delivery, broker restart, lost confirm, node partition и миграция transport.
Никакой второй реализации бизнес-статусов в Rabbit consumer.

### Общая проверка готовности

- Guest file/output доступен положенные24ч; account result не истекает сам, но квота соблюдается.
- TTL не удаляет pinned/shared input; GC действительно освобождает storage после grace/compaction.
- Hash дедупликация выдерживает одновременные одинаковые uploads без утечки чужого наличия.
- Queue position соответствует опубликованной политике; ETA показывается диапазоном/unknown.
- JSON/log скрыты без `debug=true`, а права проверяются независимо от флага.
- Named output корректен для Unicode/длинных имён/CRLF/path traversal/одинаковых base names.
- Структурированные логи связывают HTTP→job→attempt→runner→slicer и не раскрывают secrets.
- Tests fixtures внутри репозитория; runtime tests не зависят от Downloads/папок другого проекта.
- Документированы supported OS/architecture/slicer versions и действительные ограничения compact.

## 21. Дополнение: согласованная админка (2026-09-27)

Пользователь одобрил начало разработки без RabbitMQ и добавил административный интерфейс:
список аккаунтов/гостей, блокировка, сброс пароля, системные параметры и фактический/разрешённый
параллелизм. Серверная реализация первого этапа находится в профиле `server` и `/api/v2`.

Инварианты админки: ADMIN проверяется сервером, не видимостью вкладки; пароль не читается;
reset — одноразовый токен15мин с отзывом сессий; блокировка включает отмену активной работы;
нельзя блокировать себя/администратора; изменение лимита требует причины и audit event.
Настройка параллелизма не может превысить доступный worker capacity; уменьшение не прерывает
текущие jobs. Блокировка guest identity не обещает блокировку человека после смены cookies/IP.

Текущий этап намеренно не объявлен завершением всей спецификации: вместо лёгкого Rust nodeagent
пока отдельный Spring worker на общем JAR; поэтому авторасчёт может отказать native execution
на4GiB. Real Linux slicer qualification, hard scratch quotas, полная bot/compute защита и
автоматический LOST-node fencing остаются release gates. Фактические инструкции/статус:
[deploy/README.md](../../../deploy/README.md).
